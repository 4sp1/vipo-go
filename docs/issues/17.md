# Evaluate OpenAPI spec implementation vs `4sp1/vipo-flutter` spec

## Goal

Evaluate how well vipo-go implements the OpenAPI contract and compare our spec
(`openapi.json` at repo root) against the client-side spec used by
[vipo-flutter](https://github.com/4sp1/vipo-flutter/blob/c1a6ac24a09a540b20465fe90918129d08a42a9d/tooling/openapi.json).

The flutter spec is the de facto contract the real client is coded against;
vipo-go must be wire-compatible with it.

## Spec comparison (vipo-go vs vipo-flutter @ c1a6ac2)

Structurally the two specs match:

- Same paths: `POST /notes`, `GET /notes`, `GET /notes/{id}`,
  `DELETE /notes/{id}`, `POST /logs`, `GET /logs`.
- Same operationIds (`createNote`, `listNotes`, `getNote`, `deleteNote`,
  `createLogEntry`, `listLogEntries`).
- Same schemas: `PomodoroState`, `LogAction`, `CreateNoteRequest`, `Note`,
  `NoteList`, `Error`, `CreateLogEntryRequest`, `LogEntry`, `LogEntryList`.
- `LogAction` enum matches: `start`, `pause`, `reset`, `expire`, `resume`,
  `select` (`new_note` excluded from log endpoints).
- List endpoints support the same filters: `pomodoro_state` / `action` /
  `session` / `from` / `to` with `limit` (1..100, default 50) and `offset`
  (default 0).

Items to verify in detail during evaluation:

- [x] Byte-level / semantic diff of the two files — done, **zero
      differences** (structure, schemas, filters, enums, metadata all
      identical; no exception needed).
- [x] `from`/`to` `date-time` handling vs our Unix-seconds storage
      (per `docs/plans/20260614_unix-timestamps.md`) — policy settled:
      truncate to the second, inclusive bounds
      (`docs/drafts/20261012_openapi_gaps.md`, Gap 1).
- [x] `payload` is a free-form object in both specs; translation and
      SQLite storage round-trip it semantically (not byte-faithfully) via
      `json.Marshal`/`json.Unmarshal`
      (`docs/drafts/20261012_openapi_gaps.md`, Gap 2).

## Implementation evaluation

Current state in vipo-go:

- `internal/port/oapi/` — generated strict server interface and types via
  oapi-codegen v2 (regenerate with `go generate ./internal/port/oapi/`).
- `internal/port/oapi/http/translate.go` — string-to-int enum translation
  between OAPI types and domain types. Has tests (`translate_test.go`).
- `internal/svc/` and `internal/app/` are still **empty**: no service
  implementing `StrictServerInterface`, no HTTP wiring, no main entrypoint
  (`cmd/vipo-server/` empty).
- Only the `log_entries` table for `log.Entry` exists in migrations
  (added in `20260614075800.sql`); the notes table in `20260517082423.sql`.

Open questions / gaps to evaluate:

- [ ] No server runs yet, so the contract cannot be exercised end-to-end.
- [ ] `Note.created_at` / `LogEntry.timestamp` are `date-time` (RFC3339) in
      the wire format; internally stored as Unix seconds — verify translation
      covers both directions incl. `from`/`to` query params.
- [ ] `NoteList`/`LogEntryList` include a `total` field — confirm repository
      query path can return totals efficiently or whether the field should be
      dropped from the spec.
- [ ] Error responses (`Error {message, code}`) — no codepath exists yet.

## Acceptance criteria

1. Documented diff between our `openapi.json` and the flutter spec with each
   difference explained (intentional or a bug).
2. A gap list for the HTTP layer with a concrete plan (which plan files
   cover which gaps or need to be created).
3. If any wire-format mismatch is found, file follow-up work and update the
   spec or translation layer accordingly.
