# Investigate payload semantics via e2e + update OAPI spec

The OAPI spec's `payload` field (on `CreateLogEntryRequest` and `LogEntry`) is a free-form object with no schema constraints beyond "Optional action-specific data." The current implementation uses `map[string]any` with `json.Marshal`/`json.Unmarshal` round-trip (semantically lossless, not byte-faithful — see Gap 2 in `docs/drafts/20261012_openapi_gaps.md`).

After the e2e test suite from the wire-http-server plan is exercised against the Flutter client, revisit:

1. What does the Flutter client actually send in `payload`?
2. Does the spec need per-action payload schemas?
3. Should the domain layer decouple from `map[string]any` to a typed payload (revisiting the sealed `Message` interface approach)?

References: [S11] in `docs/drafts/20261021_wire_http_server_decisions.md`, Gap 2 in `docs/drafts/20261012_openapi_gaps.md`.
